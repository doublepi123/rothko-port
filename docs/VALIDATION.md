## 2026-11-20 热点共享 VPN 的 BPF 过滤器

热点选择 v2rayNG 的 `tun0` 为上游时，该接口缺少 `clsact`，热点服务挂载 IPv4 和
IPv6 接收方向过滤器均返回 `EINVAL`。netd 补丁在注册 `VpnService` 接口时创建
`clsact`，接口上已有的过滤器会保留。

ARM64 `netd` 随 `system_a` 和 `vbmeta_system_a` 刷入，17 个分区回读通过。
启动链摘要为 `21144028493372db4cfbeb17009183c6155c9cf997034f5b76d2292f41abd293`。
设备以 `user`、SELinux Enforcing 启动，连续 153 秒运行核验通过。

解锁并开启热点和 v2rayNG 后，`ap0` 选中 `tun0`，BPF 加速已开启。
`tc qdisc show dev tun0` 显示 `clsact`，`tc filter show dev tun0 ingress`
同时列出 `tether_downstream4_rawip` 和 `tether_downstream6_rawip` 两个
`direct-action` 过滤器。本轮连接没有新增 `EINVAL` 挂载错误。

## 无指纹请求时误触高亮的源码修复

旧 handler 在初始化时一直启用 touch FOD，读取到触摸驱动 DOWN 后直接开启
局部高亮；认证成功后只禁止触摸 500 ms，随后重新放开，没有与认证或录入
请求的生命周期绑定。因此系统已经结束指纹请求时，普通触摸仍可能触发高亮。

本次改为默认关闭 touch FOD，在实际认证/录入请求开始时启用。取消、成功、
错误、会话关闭、锁定或录入完成都结束高亮资格；单次识别失败仍允许当前请求
继续重试。状态、原始触摸采样和硬件写入共用互斥锁，迟到的触摸/显示事件不能
重新打开空闲传感器。

实际生产状态类的离线测试已覆盖空闲误触、有效请求、重复 DOWN、取消、
终止回调、失败重试、按住手指跨请求以及 pointer UP。可执行
`python3 tools/check-udfps-state.py` 重跑。它只验证请求门控，不代表显示硬件
或息屏解锁已经验收。三个 `hardware/xiaomi` 补丁已在固定基线上离线应用成功；
使用已有正常 Ninja 图的 11 个增量命令完成 ARM64 模块编译、链接和 strip，
动态库依赖与修复前一致。

2026-11-16 首次部署后，用户报告指纹解锁回归。复核发现新增的按住等待松开、
触摸后才允许显示采集、acquired 提前关闭 NIT 均改变了原先有效的认证时序。
后续修正保留请求门控，恢复显示事件控制采集；真实按住触摸可在请求开始后
进入接触。新增回归测试覆盖显示/触摸两种顺序、acquired 早于显示结束及按住
唤醒，旧状态机失败、修正后通过。服务已重编，并启用普通状态的 Logd 输出。
这仍是待手机实测的修复候选，不能由离线测试判定亮屏或息屏解锁已恢复。

### 2026-11-17：静态 handler 的 V1/V2 ABI 错配

用户最终反馈亮屏、息屏均不能解锁。失败时系统已有 Keyguard 认证请求，无
强认证限制、锁定或 HAL death；触摸、面板高亮和显示事件存在，但没有有效
采集或匹配回调。

使用实际 Ninja 编译命令和真实 Android 头文件构造 ARM64 布局探针，确认服务
带 `-DIMPL_V2`，独立编译的静态 handler 却没有该标志。handler 所见的
`extCmd` 偏移为 208，恰好是 V2 服务的 `authenticate` 偏移；V2 的真正
`extCmd` 偏移为 240。因此每次触摸/采集命令实际重启了认证，没有传给正确
的扩展命令入口。这解释了命令返回成功却无有效采集的现象；单独修改时序
不能修复此问题。

服务及共享/静态 handler 现共用 V2 编译默认项，handler 增加 V1 编译错误。
`tools/check-udfps-abi.py` 使用生成图中的实际 ARM64 编译参数核对两边函数表，
并验证删去 V2 标志后生产 handler 编译失败。重编后两边 `extCmd` 均为 240。
新产物已完成 AVB/FEC 校验、刷入及完整 17 分区回读，连续 153 秒 USER 启动、
IMS/指纹服务及包 UID 核验通过；SELinux 保持 Enforcing。
当前启动链摘要为 `cce61debdbadfa3c1c21059243c5016d9867c8f9871eeb2ac063c85dfb7b82dd`。
2026-11-17 用户明确确认该 V2 接口修复版“亮屏、熄屏都能解锁”，据此记录
两种解锁已通过本轮手机实测。之后 USB 已断开，未补采这次成功操作的日志；
此前的分区回读和运行核验记录保持原样。空闲误触高亮及用户手动通话仍待
本轮反馈，不能由解锁通过推定它们也通过。

## 离线源码缓存中的 Git LFS 输入

初次空输出构建在 Chromium WebView 的正常 `uses-library` 检查处停止：
`webview.apk` 实际是 134 字节的 Git LFS 指针，APK 工具无法打开。所需真实
APK 在原本地对象缓存中存在，尺寸和 SHA-256 与固定提交的指针完全匹配。
补齐实体后，原失败命令原样重跑通过，没有放宽校验。

准备工具现会读取固定提交的 `filter=lfs` 属性，创建目的目录前校验所需
本地实体，检出后独立复制并再次验哈希。普通测试文件即使内容类似 LFS 指针，
只要没有声明 LFS 过滤就保持原样。缺失实体时提前报错，继续禁止下载。

十项真实临时 Git LFS 仓库测试通过；包含四个架构 WebView 和一个普通 Rust
测试数据项目的真实 repo 检出也在仅允许本地套接字的环境中通过。
这证明离线输入准备修复。2026-11-16 后续空输出开发构建和产物核验已通过，
详见[构建记录](CLEAN-BUILD.md)。
